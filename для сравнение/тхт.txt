Принимаю все шесть замечаний — по каждому конкретное решение, без воды.

**1. Статус урока — на `enrollment`, а не в `lessons`**

Согласен, это была ошибка. `lessons` — это общий каталог (контент, порядок, привязка к модулю), одинаковый для всех учеников. Статус прохождения — персональный. Нужна отдельная таблица:

```
enrollment_lesson_status (
  id,
  enrollment_id -> enrollments.id,
  lesson_id     -> lessons.id,
  status        (locked | available | in_progress | completed),
  completed_at  nullable,
  unique(enrollment_id, lesson_id)
)
```

Соответственно `lesson_unlock_log` тоже нужно перепривязать: не `student_id + lesson_id`, а `enrollment_id + lesson_id` — иначе при повторном зачислении (раздел 3.2 в v3) история открытий перемешается между заходами.

**2. Таблица расписания — её действительно не было**

В v3 «занятие» упоминалось только как атрибут посещаемости, без своей сущности. Добавляю (имя `class_sessions`, чтобы не путать с `sessions` авторизации):

```
class_sessions (
  id,
  group_id    -> groups.id,
  teacher_id  -> users.id,
  lesson_id   nullable -> lessons.id,   -- если занятие привязано к конкретному уроку каталога
  date, start_time, end_time,
  type        (lesson | call | makeup | other),  -- те же типы, что маркеры в календаре
  format      (offline | online),
  location_or_link
)
```

`attendance` теперь ссылается на `class_session_id`, а не абстрактное «занятие». `makeup_lessons` тоже ссылается на `class_session_id` — конкретную новую сессию, созданную под отработку.

**3. Связь `payments` ↔ `invoices`**

Сейчас это неявная связь «каждый платёж привязан к одному или нескольким инвойсам» — без таблицы это не реализуемо, если платёж покрывает два месяца сразу или инвойс закрывается частями. Нужна junction-таблица:

```
payment_allocations (
  id,
  payment_id -> payments.id,
  invoice_id -> invoices.id,
  amount
)
```

Статус инвойса (`paid`/`pending`/`overdue`) считается как сумма `amount` по всем его `payment_allocations` относительно суммы инвойса.

**4. Схема прав**

Роль сама по себе (ADMIN/TEACHER/STUDENT/PARENT) — слишком грубая гранулярность для API-уровня. Добавляю явную матрицу:

```
permissions       (id, code)              -- например: lesson.unlock_early, progress.override, submission.grade, attendance.mark
role_permissions  (role_id, permission_id)
```

Но одних permissions мало — нужен ещё **row-level** контроль: TEACHER с правом `submission.grade` должен видеть/проверять только сдачи учеников из **своих** групп, а не вообще всех. Это завязано на пункт 5 ниже.

**5. Связь преподавателей с группами**

Тоже отсутствовала — было неявно «у группы есть преподаватель», но без таблицы это не поддерживает ни со-преподавание, ни ведение одним преподавателем нескольких групп. Добавляю:

```
group_teachers (
  group_id   -> groups.id,
  teacher_id -> users.id,
  role_in_group (main | assistant),
  primary key(group_id, teacher_id)
)
```

Это и есть механизм row-level проверки из пункта 4: на API-уровне доступ TEACHER к ученику/сдаче/занятию проверяется через «состоит ли teacher_id в group_teachers той группы, к которой относится enrollment/class_session».

**6. Противоречие 6 проектных дней и 52 слотов**

Согласен, это прямая нестыковка: 13 недель × 4 = 52 слота, из них 50 уже заняты обычными уроками — свободных 2, а не 6. Как я написал раньше — противоречие. Убираю лишнее требование, а не подгоняю цифры:

Уроки-финалки блоков (10, 16, 24, 32, 40, 50) и так по описанию в поурочном плане включают «финализацию проекта» внутри самого урока — отдельный незанумерованный день сверху не нужен, это уже часть тех же 50 слотов. Формулировку про «6 дополнительных проектных дней сверх счётчика» убираю как ошибочную. Единственный реальный буфер — 2 свободных слота из 52, оставляю их под праздники/повторение, как и было изначально.

Если по факту ученикам нужно физически больше времени на финальные проекты блоков — это не решается «доп. днём без темы», а либо сдвигом графика (14 недель вместо 13), либо тем, что срок сдачи ДЗ для этих 6 уроков сознательно длиннее одного межурочного интервала (например, 2 занятия на сдачу вместо одного) — это конфигурируется на уровне `assignments.due_offset`, а не отдельной сущностью в календаре.

**7. Двойной учёт финального проекта в формуле прогресса**

Тоже верно замечено — урок 50 и его сдача (задание 50) сейчас попадают одновременно в 40%-долю уроков, в 40%-долю ДЗ (через `accepted_submissions/total_assignments`) и ещё раз отдельно в 20% `final_project_status` — финальный проект получает завышенный вес.

Фикс: задание 50 (финальный ML-проект) **исключается** из знаменателя и числителя 40%-компоненты ДЗ. То есть в формуле:

```
progress_calculated =
    40 × (completed_lessons / 50)
  + 40 × (accepted_submissions / 49) × (avg_grade_of_accepted_submissions / 100)   -- задания 1–49, без финального проекта
  + 20 × final_project_status   -- только сдача задания 50
```

Прохождение самого урока 50 (просмотр материала) по-прежнему учитывается в 40%-доле уроков (`completed_lessons/50`) — это отдельный сигнал «открыл финальный урок», не пересекается с оценкой за проект. А вот оценка/статус сдачи проекта учитывается ровно один раз — в 20%-блоке.
