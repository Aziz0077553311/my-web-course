## 1. Общая концепция

Единая образовательная платформа из пяти логических частей на одной базе данных и одном API:

1. **Публичный сайт** — лендинг, программа курса, стоимость, запись.
2. **Кабинет ученика** — уроки, ДЗ, прогресс, посещаемость, чат, профиль.
3. **Кабинет преподавателя** — ученики, уроки, проверка ДЗ, посещаемость, оценки.
4. **Админ-панель** — полное управление платформой.
5. **Единая PostgreSQL база данных** для всех частей.

Система адаптивна: ПК, планшет, телефон. Регистрация с сайта автоматически создаёт аккаунт в системе — второй отдельной базы для сайта нет.

## 2. Структура курса

Продолжительность — 3 месяца, 50 уроков (40 — программирование, 10 — Machine Learning).

### 2.1 Блоки

**Месяцы 1–2 — программирование**
- Блок 1. Основы программирования (5 уроков)
- Блок 2. HTML (5 уроков)
- Блок 3. CSS (6 уроков)
- Блок 4. JavaScript (8 уроков)
- Блок 5. React (8 уроков)
- Блок 6. Python + Backend (8 уроков)

**Месяц 3 — Machine Learning** (10 уроков): AI/ML/DL, NumPy, Pandas, визуализация и статистика, supervised learning (регрессия, классификация), метрики, train/test split и переобучение, нейросети, финальный ML-проект.

### 2.2 Детальный поурочный план

Полная таблица 50 уроков (тема / что внутри / ДЗ) сохраняется без изменений из `ТЗ_образовательная_платформа_v2_.md`, разделы 2.1–2.2 — это исходный источник правды по содержанию уроков. В этом документе не дублируется полностью, чтобы не расходиться с оригиналом при будущих правках содержания; при разработке брать таблицу оттуда как есть.

Кратко по нумерации: уроки 1–5 — Блок 1, 6–10 — Блок 2, 11–16 — Блок 3, 17–24 — Блок 4, 25–32 — Блок 5, 33–40 — Блок 6, 41–50 — ML.

### 2.3 Единые контрольные цифры (используются везде — на дашборде, в успеваемости, в примерах для дизайнера)

Чтобы во всех макетах и примерах фигурировали одни и те же цифры:

- Всего уроков: **50**
- Всего заданий (ДЗ): **50** (каждому уроку соответствует одно задание, включая финальные проекты блоков и финальный ML-проект — урок 50)
- Пример прогресса «среднего» ученика на середину курса: пройдено уроков **32/50**, сдано и принято ДЗ **28/50**, средняя оценка **91%**, посещаемость **94%**, общий прогресс **78%**

Эти цифры — единственный источник примеров для UI-макетов; если дизайнер или разработчик встречает где-то другие «демо-цифры», они устарели.

### 2.4 Реалистичность нагрузки (расчёт темпа)

50 уроков за 3 месяца (≈ 13 недель) требуют явно зафиксированного темпа занятий — без этого непонятно, реалистична ли программа:

- 13 недель × **4 занятия в неделю** = 52 «слота» — с запасом покрывает 50 уроков (2 слота остаются на праздники/повторение/буферные дни).
- Это соответствует формату интенсивного курса (почти full-time, 4 дня в неделю), а не «раз в неделю по вечерам» — если задумывался более лёгкий темп (1–2 занятия в неделю), 50 уроков физически не укладываются в 3 месяца, и либо сокращается программа, либо увеличивается срок курса.
- Каждый урок предполагает домашнее задание, выполняемое учеником самостоятельно между занятиями — при 4 занятиях в неделю на одно ДЗ у ученика в среднем 1–2 дня, чего достаточно для практических заданий уровня «мини-скрипт/страница/компонент», но тесно для «финального проекта блока» (уроки 10, 16, 24, 32, 40) и особенно для финального ML-проекта (урок 50) — по этим 6 урокам рекомендуется закладывать дополнительный день без новой темы («проектный день») сверх счётчика уроков.

**Зафиксировано как параметр курса:** 4 занятия в неделю, дополнительные непронумерованные проектные дни для итоговых работ блоков — не входят в счётчик «50 уроков», но входят в календарь занятий.

## 3. Роли и модель данных — явные связи

Раньше часть сущностей была неявной (роль «зашита» в пользователя, не было общей точки, к которой привязаны прогресс/оценки/оплата одного зачисления). Ниже — явная схема.

### 3.1 Пользователь и роль

```
users (id, email, password_hash, full_name, created_at)
roles (id, code: ADMIN | TEACHER | STUDENT | PARENT)
user_roles (user_id, role_id)   -- многие-ко-многим: у пользователя может быть больше одной роли в будущем
                                 -- (например, преподаватель тоже может быть учеником ML-модуля)
```

### 3.2 Зачисление — ключевая связующая сущность

`enrollments` — это то, чего не хватало в исходном ТЗ: единая точка, которая связывает ученика с конкретным курсом/группой/потоком, и к которой привязывается **всё остальное** (прогресс, оценки, инвойсы), а не напрямую к `user_id`. Это важно, если ученик когда-нибудь проходит курс повторно или переводится в другую группу — история не должна смешиваться.

```
enrollments (
  id,
  student_id       -> users.id,
  group_id         -> groups.id,
  course_id        -> courses.id,
  status           -- active | paused | completed | expelled
  enrolled_at,
  completed_at nullable
)
```

Связь: `Student → Enrollment → Group → Course → Module → Lesson → Assignment → Submission (N попыток) → Grade`

Прогресс, инвойсы и итоговая посещаемость считаются **в рамках одного `enrollment_id`**, а не «вообще по ученику» — так корректно обрабатывается кейс повторного зачисления.

### 3.3 Полная схема таблиц (обновлено)

```
users · roles · user_roles · sessions
students · teachers · admins · parent_student
groups · courses · modules · lessons · lesson_unlock_log
enrollments
assignments · submissions (+ attempt_number) · grades
attendance · attendance_reasons (+ decision_type, decided_by) · makeup_lessons
invoices (+ enrollment_id) · payments
progress (+ enrollment_id, progress_calculated, progress_override) · progress_override_log
files · profiles
messages · notifications
projects
```

### 3.4 Ключевые связи (итог)

```
User → Enrollment → Group → Course → Module → Lesson → Assignment → Submission (N попыток) → Grade
Attendance → Attendance_reason → Makeup_lesson | Invoice (корректировка)
Enrollment → Invoice (за период) → Payment (факт оплаты)
Enrollment → Progress (progress_calculated / progress_override)
```

## 5. Формула расчёта прогресса (зафиксировано)

`progress_calculated` считается автоматически по формуле, в рамках одного `enrollment_id`:

```
progress_calculated (%) =
    40 × (completed_lessons / total_lessons)
  + 40 × (accepted_submissions / total_assignments) × (avg_grade_of_accepted_submissions / 100)
  + 20 × final_project_status

где final_project_status:
  0    — финальный ML-проект (урок 50) не сдан
  0.5  — сдан, на проверке / требует исправления
  1    — принят преподавателем
```

- `progress_override` — nullable-поле; если преподаватель/админ скорректировал прогресс вручную, значение и обоснование (`override_reason`) хранятся здесь.
- Интерфейс всегда показывает `progress_override`, если оно заполнено, иначе `progress_calculated`.
- Любое ручное изменение логируется в `progress_override_log`: кто, когда, значение до/после, причина.
- Точные веса (40/40/20) — дефолтное значение по этому ТЗ; если бизнес хочет другие пропорции, менять нужно централизованно (одна константа/конфиг), а не в каждом месте расчёта отдельно.

## 6. Система уроков

Каждый урок — отдельная страница: номер, название, описание, теория, видео/материалы, примеры кода, доп. материалы, домашнее задание, кнопка «Урок пройден», статус (раздел 4).

**Логика открытия:**

- По умолчанию — строго последовательное открытие: урок N+1 становится доступен только после того, как урок N получил статус `completed`.
- Исключение — преподаватель может вручную открыть любой урок досрочно кнопкой «Открыть досрочно» (сценарий — раздел 12.3).
- Каждое досрочное открытие логируется в `lesson_unlock_log`: `opened_by`, `opened_at`, `lesson_id`, `student_id`.

## 7. Домашние задания и проверка

Ученик выполняет задание и жмёт Submit: текстовый ответ, ссылка на GitHub, ссылка на проект, файлы, комментарий.

Преподаватель видит очередь на проверку: ученик, урок, задание, дата отправки, ответ, ссылки, файлы. Ставит оценку (0–100) и комментарий. Пошаговый сценарий проверки — раздел 12.1.

**Логика повторной отправки:**

- Если статус `needs_revision`, ученик отправляет работу заново — это **новая запись**, а не перезапись старой.
- Таблица `submissions` хранит `attempt_number` (1, 2, 3…) для пары (enrollment, задание).
- Каждая попытка хранит свой ответ, файлы, оценку, комментарий и дату — история не теряется.
- В интерфейсе по умолчанию показывается последняя попытка, доступен просмотр всей истории.
- Итоговая оценка по заданию = оценка последней принятой попытки (если не переопределено вручную).

## 8. Посещаемость и отработки

Преподаватель создаёт занятия (дата, время, тема, группа) — ученики группы автоматически видят их в календаре. После занятия преподаватель отмечает каждого ученика статусом из раздела 4.

**Логика обработки пропуска:**

- Запись `attendance` — единственный источник правды по конкретному пропуску.
- Если причина «уважительная» — создаётся `attendance_reasons` с `decision_type` (`makeup_lesson` или `payment_adjustment`) и `decided_by`.
- Решение принимается **не позднее 7 дней** после пропуска (настраивается администратором) — иначе статус автоматически становится `absent_unresolved`.
- Один пропуск — только одно решение: либо отработка (`makeup_lessons`), либо корректировка оплаты, но не оба сразу (ограничение на уровне БД, unique-связь).
- Пошаговый сценарий принятия решения преподавателем — раздел 12.2.

## 9. Оплата

Базовая стоимость — 4000/мес. Начисление и факт оплаты разделены:

- `invoices` — начисление за период: сумма, период, статус (раздел 4), `enrollment_id`, ссылка на `attendance_reasons`, если сумма скорректирована из-за пропуска.
- `payments` — фактические платежи, каждый привязан к одному или нескольким `invoices`.
- Статус ученика («оплачено»/«должен») вычисляется из соотношения `invoices` и `payments`, не хранится отдельным несинхронизируемым полем.

## 12. Кабинет преподавателя — сценарии и UI

### 12.1 Сценарий: проверка домашнего задания

1. Преподаватель открывает «Домашние задания» → фильтр «На проверке» (статус `submitted`).
2. Открывает конкретную сдачу: видит ответ, ссылки, файлы, комментарий ученика, номер попытки (`attempt_number`) и историю прошлых попыток, если это не первая.
3. Ставит оценку (0–100) и комментарий.
4. Выбирает итоговый статус: `accepted` (принято) или `needs_revision` (на доработку).
5. Система создаёт запись `grade`, статус `submission` обновляется, ученику приходит уведомление (раздел 15), `progress_calculated` пересчитывается автоматически.

### 12.2 Сценарий: обработка пропуска (уважительная причина)

1. После занятия преподаватель отмечает ученика статусом `absent` и указывает причину.
2. Если причина уважительная — создаётся `attendance_reasons` со статусом «решение не принято» (`excused_pending`).
3. В течение 7 дней преподаватель (или админ) принимает решение: назначить отработку (`makeup_lesson`, выбирается дата/занятие из календаря) **или** скорректировать оплату (`payment_adjustment`, указывается сумма/период).
4. Система проставляет `decision_type`, `decided_by`, дату решения; статус `attendance` меняется на `excused_makeup` или `excused_payment_adjustment`.
5. Если 7 дней прошло без решения — статус автоматически становится `absent_unresolved`, ученику и преподавателю приходит напоминание заранее (за 1–2 дня до истечения срока).

### 12.3 Сценарий: досрочное открытие урока

1. На странице ученика (карточка курса/прогресса) преподаватель видит список уроков со статусами.
2. Рядом с заблокированным (`locked`) уроком — кнопка «Открыть досрочно».
3. Преподаватель подтверждает действие (модальное окно с обязательным полем «причина» — для истории).
4. Статус урока для конкретного ученика меняется на `available`, создаётся запись в `lesson_unlock_log` (`opened_by`, `opened_at`, `lesson_id`, `student_id`, `reason`).
5. Действие видно в карточке ученика во вкладке «История» и в логах админки (раздел 13).

### 12.4 Сценарий: ручная корректировка прогресса (override)

1. На карточке ученика преподаватель/админ нажимает «Скорректировать прогресс».
2. Вводит новое значение (%) и обязательное текстовое обоснование.
3. Система сохраняет `progress_override`, `override_by`, `override_at`, `previous_value` (было — рассчитанное значение) в `progress_override_log`.
4. Везде в интерфейсе (кабинет ученика, кабинет преподавателя, админка) с этого момента показывается `progress_override` вместо `progress_calculated`, пока его не сбросят.

### 12.5 Dashboard преподавателя

Количество учеников, занятия сегодня, ДЗ на проверке, средняя успеваемость, посещаемость, неоплаченные месяцы.

**Карточка ученика:** профиль, прогресс, оценки, ДЗ, посещаемость, пропуски, платежи, комментарии преподавателя, история изменений (лог override'ов и досрочных открытий из 12.3–12.4).

## 13. Админ-панель

Полное управление: ученики, преподаватели, группы, курсы, уроки, ДЗ, календарь, посещаемость, оценки, платежи, чаты, пользователи, роли, настройки платформы + просмотр всех логов ручных решений.

### 13.1 Принцип честной статистики

Все KPI считаются из тех же таблиц, что и остальная платформа (раздел 3), не из отдельного «декоративного» слоя:

- Если ученик не начал курс — у него везде **0**: 0 пройденных уроков, 0% прогресс, 0 сданных ДЗ, «—» вместо оценки (оценка не существует, пока нет хотя бы одной принятой попытки).
- Средние по группе/курсу считаются **с учётом нулей** неактивных учеников.
- Пустое состояние (0 активности) — нормальный статус, отображается нейтральным серым (как `locked`/`available` в разделе 4), не красным «ошибка».

### 13.2 Структура

**Sidebar:** Главная · Ученики · Преподаватели · Группы · Курсы · Уроки · ДЗ · Календарь · Посещаемость · Оценки · Платежи · Чаты · Пользователи и роли · Настройки · Логи.

**Верхние KPI:** всего учеников, активных учеников (есть ≥1 пройденный урок за 30 дней), средняя посещаемость по платформе, доля оплаченных инвойсов за текущий месяц.

**Графики:** динамика новых зачислений по месяцам; распределение учеников по блокам курса (на каком блоке сейчас находится каждая группа).

**Таблица учеников:** имя, группа, пройдено уроков, средняя оценка, посещаемость, статус оплаты — строка ученика без активности показывает `0` во всех колонках и бейдж «Не начал» (не пустые ячейки).

**Логи ручных решений:** отдельная вкладка — кто, когда, что изменил (досрочное открытие, override прогресса, решение по пропуску).

## 19. База данных — сводная схема

PostgreSQL, единая для всех частей системы. Полный список таблиц и связей — разделы 3.3–3.4. Отличия от самой первой версии ТЗ:

- Добавлена `enrollments` — явная связь ученика с курсом/группой, к которой привязаны прогресс, оценки и инвойсы (закрывает замечание про неявные связи).
- `submissions` хранит историю попыток (`attempt_number`), а не одну запись на пару (ученик, задание).
- `attendance_reasons` явно связана с `makeup_lessons` ИЛИ с корректировкой в `invoices`, но не с обоими одновременно.
- `invoices` отделены от `payments`.
- `sessions` (выход со всех устройств), `roles`/`user_roles` и `parent_student` — для расширяемого RBAC.
- `files` — единое хранилище вложений вместо полей в разных таблицах.
- `lesson_unlock_log` и `progress_override_log` — аудит ручных решений.

## 20. Авторизация и роли

Email/пароль, восстановление и смена пароля, выход со всех устройств (через `sessions`/refresh-токены). Telegram-вход — в следующих версиях. После входа роль определяется по `user_roles`.

**ADMIN** — полный доступ.
**TEACHER** — ученики, уроки, ДЗ, посещаемость, оценки, чаты своих групп.
**STUDENT** — свой курс, профиль, ДЗ, прогресс, календарь, чат.
**PARENT** (на будущее) — просмотр посещаемости, успеваемости, прогресса, оплаты, ДЗ своего ребёнка через `parent_student` (родитель может быть привязан к нескольким ученикам, ученик — к нескольким родителям).

## 21. Технологический стек

**Frontend:** React + TypeScript, React Router, адаптивная вёрстка, shadcn/ui + Tailwind (раздел 16.6).

**Backend:** Python + FastAPI, REST API, JWT authentication, RBAC, WebSocket-слой для чата и live-уведомлений.

**Database:** PostgreSQL + SQLAlchemy.

**Файлы:** отдельное object storage (изображения, домашки, аватары), доступ через единую таблицу `files`.

**Deployment:** frontend и backend отдельно, работают через API с одной PostgreSQL-базой.

## 26. Итоговая схема ролей и сценариев

**Ученик:** заходит → проходит уроки последовательно (или досрочно с разрешения) → получает и сдаёт ДЗ (с историей попыток) → получает оценку → видит прогресс (расчётный или скорректированный) → посещает занятия → при пропуске получает отработку или корректировку оплаты → общается в чате.

**Преподаватель:** видит учеников → проводит занятия → отмечает посещаемость → в течение 7 дней принимает решение по уважительным пропускам (12.2) → выдаёт и проверяет ДЗ (12.1) → ставит оценки → может вручную открыть урок досрочно (12.3) или скорректировать прогресс (12.4) — с логированием.

**Администратор:** управляет пользователями, ролями, курсами, платежами, группами, преподавателями, контентом и видит все логи ручных решений (13).
